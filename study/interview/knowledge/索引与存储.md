## similaritySearch 与 similarityThreshold 对比

> **模块**：索引与存储 | **标签**：索引与存储 | **更新**：2026-05-28

### 核心概念

文档 1「猫咪需要高蛋白食物」→ 0.92；文档 2「猫咪喜欢睡觉」→ 0.35；文档 3「狗狗需要运动」→ 0.12

### 要点

**核心区别**：

| 特性 | similaritySearch（无阈值） | similarityThreshold（带阈值） |
| :--- | :--- | :--- |
| 核心理念 | 数量优先，保证返回 topK 条 | 质量优先，只返回超过阈值的结果 |
| 返回数量 | **固定为 K**（低分也可能被返回） | **不固定**（可能少于 K，甚至为 0） |
| 文档质量 | 可能混入不相关内容 | 阈值过滤，结果更精准 |
| 典型场景 | 对数量有硬性要求，或需二次过滤 | 对准确性要求高，避免低质量噪声 |

**举例**（检索「猫咪吃什么比较好？」）：

- 文档 1「猫咪需要高蛋白食物」→ 0.92；文档 2「猫咪喜欢睡觉」→ 0.35；文档 3「狗狗需要运动」→ 0.12
- **topK=2 无阈值**：返回文档 1、2（为凑够数量，低分文档 2 也被返回）
- **阈值=0.7**：仅返回文档 1；即使 topK=10 也只返回 1 条

**常量 `SIMILARITY_THRESHOLD_ACCEPT_ALL`**：值为 `0.0`，接受所有文档（得分 ≥ 0），效果等同于普通 `similaritySearch`。

### 代码示例

```java
SearchRequest request = SearchRequest.query("用户问题")
        .withTopK(5)
        .withSimilarityThreshold(SearchRequest.SIMILARITY_THRESHOLD_ACCEPT_ALL);

List<Document> results = vectorStore.similaritySearch(request);
```

```java
SearchRequest request = SearchRequest.query("用户问题")
        .withTopK(10)
        .withSimilarityThreshold(0.75);

List<Document> results = vectorStore.similaritySearch(request);
```

### 面试常问

**问**：Spring AI VectorStore 中 `similaritySearch` 与基于 `similarityThreshold` 的检索有何区别？`SIMILARITY_THRESHOLD_ACCEPT_ALL` 是什么？

**答**：文档 1「猫咪需要高蛋白食物」→ 0.92；文档 2「猫咪喜欢睡觉」→ 0.35；文档 3「狗狗需要运动」→ 0.12；topK=2 无阈值**：返回文档 1、2（为凑够数量，低分文档 2 也被返回）；阈值=0.7**：仅返回文档 1；即使 topK=10 也只返回 1 条。

通过 `SearchRequest` 的 `withFilterExpression` 传入 `Filter.Expression` 组合条件，配合 `withTopK(5)` 与 `withSimilarityThreshold` 发起检索。

### 要点

## 向量索引优化 HNSW 与 IVFFlat

> **模块**：索引与存储 | **标签**：索引与存储 | **更新**：2026-05-28

### 核心概念

HNSW：低延迟、高召回，内存占用大，适合在线检索。

### 要点

- **HNSW**：低延迟、高召回，内存占用大，适合在线检索。
- **IVF / IVFFlat**：内存友好、构建快，需训练，召回略低。
- **DiskANN**：SSD 场景下平衡延迟与容量。
- **PgVector**：可设 `index-type: HNSW`，调 `m`、`ef_construction`。
- **Redis**：可选 `Algorithm.HNSW`，配置 `hnswM`、`hnswEfConstruction`。

### 代码示例

```yaml
spring:
  ai:
    vectorstore:
      pgvector:
        index-type: HNSW
        distance-type: COSINE_DISTANCE
        dimensions: 1536
```

```java
RedisVectorStore vectorStore = RedisVectorStore.builder(jedisPooled, embeddingModel)
    .indexName("my_vector_index")
    .vectorAlgorithm(Algorithm.HNSW)
    .hnswM(32)
    .hnswEfConstruction(200)
    .build();
```

### 面试常问

**问**：如何利用索引类型选择（HNSW、IVF_FLAT）以及分区/分片策略优化检索性能？请结合 Milvus、PgVector 或 Redis 给出配置建议。

**答**：HNSW**：低延迟、高召回，内存占用大，适合在线检索。；IVF / IVFFlat**：内存友好、构建快，需训练，召回略低。；DiskANN**：SSD 场景下平衡延迟与容量。；PgVector**：可设 `index-type: HNSW`，调 `m`、`ef_construction`。。

## 多租户数据隔离

> **模块**：索引与存储 | **标签**：索引与存储 | **更新**：2026-05-28

### 核心概念

写入：在 metadata 强制注入 `tenant_id`。

### 要点

- **写入**：在 metadata 强制注入 `tenant_id`。
- **检索**：用 `Filter.ExpressionBuilder.eq("tenant_id", currentTenantId)` 与 SearchRequest 组合，确保仅命中本租户数据。

### 代码示例

```java
// 插入时强制注入 tenant_id
public void addDocument(String content, Map<String, Object> extraMetadata) {
    String tenantId = tenantSecurityUtil.getCurrentTenantId();
    Map<String, Object> metadata = new HashMap<>(extraMetadata);
    metadata.put("tenant_id", tenantId);
    Document doc = new Document(content, metadata);
    vectorStore.add(List.of(doc));
}

// 检索时动态过滤
public List<Document> searchByTenant(String query, int topK) {
    String tenantId = tenantSecurityUtil.getCurrentTenantId();
    Filter.Expression tenantFilter = Filter.ExpressionBuilder.eq("tenant_id", tenantId);
    SearchRequest searchRequest = SearchRequest.query(query)
            .withTopK(topK)
            .withFilterExpression(tenantFilter);
    return vectorStore.similaritySearch(searchRequest);
}
```

### 面试常问

**问**：如何利用元数据过滤实现租户级别的数据隔离？请给出插入和检索时的代码示例。

**答**：写入**：在 metadata 强制注入 `tenant_id`。；检索**：用 `Filter.ExpressionBuilder.eq("tenant_id", currentTenantId)` 与 SearchRequest 组合，确保仅命中本租户数据。。

### 核心概念

分片键：合理选择 routing 字段，避免热点分片。

### 要点

- **分片键**：合理选择 routing 字段，避免热点分片。
- **分片大小**：单分片建议 10GB–50GB，过多小分片增加协调开销。

```yaml
  index:
    refresh_interval: 30s
```

## Elasticsearch routing 精确查找

> **模块**：索引与存储 | **标签**：索引与存储 | **更新**：2026-05-28

### 核心概念

写入侧：在 `@Document` 或映射中指定 `routing` 字段（如 `customerId`），使同一租户/客户文档落在同一分片。

### 要点

- **写入侧**：在 `@Document` 或映射中指定 `routing` 字段（如 `customerId`），使同一租户/客户文档落在同一分片。
- **查询侧**：`SearchRequest` 携带相同 routing 值，检索仅命中目标分片。
- **收益**：缩小搜索范围、降低延迟，适合多租户或按业务键分区场景。

### 代码示例

```java
@Document(indexName = "orders", routing = "customerId")
public class Order { ... }

SearchRequest request = SearchRequest.of(q -> q
    .index("orders")
    .routing("cust_123")
    .query(...)
);
```

**问**：如何利用 Elasticsearch routing 减少跨分片扫描、加速精确查找？

**答**：写入侧**：在 `@Document` 或映射中指定 `routing` 字段（如 `customerId`），使同一租户/客户文档落在同一分片。；查询侧**：`SearchRequest` 携带相同 routing 值，检索仅命中目标分片。；收益**：缩小搜索范围、降低延迟，适合多租户或按业务键分区场景。。

## ANN 近似最近邻搜索

> **模块**：索引与存储 | **标签**：向量索引, ANN | **更新**：2026-05-28

### 核心概念

ANN（Approximate Nearest Neighbor）在海量高维向量中用**精度换速度**，快速找到「足够相似」的邻居，是向量检索的底层加速手段。

### 要点

| 算法 | 特点 |
| :--- | :--- |
| **HNSW** | 分层可导航小世界图，低延迟高召回，内存占用较大 |
| **IVF** | 倒排文件索引，构建快、内存友好，需训练，召回略低 |
| **LSH** | 局部敏感哈希，适合超大规模近似匹配 |

- 与精确最近邻相比，ANN 牺牲少量召回换取数量级速度提升。
- 生产选型常组合：**HNSW 在线检索 + IVF 冷数据分区**；Spring AI 侧见 PgVector/Redis 的 HNSW 配置。

### 代码示例

```python
import faiss
import numpy as np

dim = 128
data = np.random.random((10000, dim)).astype('float32')

# HNSW 索引，32 为每层最大连接数
index = faiss.IndexHNSWFlat(dim, 32)
index.add(data)

query = np.random.random((1, dim)).astype('float32')
distances, indices = index.search(query, k=5)
```

### 面试常问

**问**：向量检索为什么普遍使用 ANN 而非精确搜索？常见算法有哪些？

**答**：高维空间精确最近邻成本极高；ANN 用可控精度损失换速度。主流有 HNSW（低延迟高召回）、IVF（内存友好）、LSH（超大规模哈希近似）。

## 个人知识库存储介质选型

> **模块**：索引与存储 | **标签**：VectorStore, 图数据库 | **更新**：2026-05-28

### 核心概念

个人/小型知识库选型需按任务类型在**语义检索、关键词精确匹配、多跳图推理**之间权衡介质与运维成本。

### 要点

**纯 RAG（向量为主）**

| 方案 | 介质 | 特点 |
| :--- | :--- | :--- |
| 轻量级 | Chroma + 本地文件 | 零配置，内存索引 |
| 高召回 | PostgreSQL + pgvector | 向量 + 全文混合查询 |
| 嵌入式 | SQLite + sqlite-vec | 单文件，便携 |

**GraphRAG（需图存储）**

| 类型 | 代表 | 优点 | 资源 |
| :--- | :--- | :--- | :--- |
| 嵌入式图库 | KùzuDB | 列式、无服务 | 低（<500MB） |
| 分析融合 | DuckDB + 图扩展 | 单文件 SQL 统一 | 低 |
| 开箱即用 | fathomdb（SQLite） | 图+向量+全文 | 很低 |
| 传统重型 | Neo4j（Docker） | 功能最全 | 高（≥1GB） |

**任务 → 介质速查**

| 任务 | 推荐 | 理由 |
| :--- | :--- | :--- |
| 简单 QA | Chroma | 语义匹配快 |
| 精确关键词 | SQLite FTS5 | 毫秒级、无依赖 |
| 多跳关系问答 | KùzuDB / Neo4j | 图遍历效率高 |
| 个人笔记+图谱 | fathomdb / Trilium | 零运维便携 |
| 海量分析 | DuckDB + 图扩展 | SQL 统一分析 |

- 微软 GraphRAG 推荐配置：约 32GB 内存；索引体积约为源文件 10 倍。

### 面试常问

**问**：个人电脑上搭建小型 RAG 知识库，向量检索和 GraphRAG 分别怎么选型？

**答**：纯向量 RAG 可用 Chroma（轻量）或 pgvector（混合查询）；需多跳推理时用 KùzuDB/fathomdb 等嵌入式图库，功能要求高再上 Neo4j。按任务选介质，避免为小库过度部署。

## ChromaDB 概述与数据模型

> **模块**：索引与存储 | **标签**：ChromaDB, VectorStore, RAG | **更新**：2026-05-28

### 核心概念

ChromaDB 是面向 AI 应用的开源向量数据库，以轻量、API 友好著称，用于持久化 embedding 并执行语义相似检索，常被用作 RAG 原型与学习型项目的首选向量库。

### 要点

**核心职责**

| 职责 | 说明 |
| :--- | :--- |
| 向量存储与管理 | 将非结构化文本等转为 embedding 后持久化 |
| 语义检索 | 按查询向量语义返回 Top-K 相似结果（余弦/欧氏距离等） |
| 支撑 RAG | 作为外部知识库，为大模型提供检索上下文 |
| 元数据过滤 | 在语义搜索基础上附加 `where` 条件过滤结果 |

**数据模型**（类比关系型数据库）

| 概念 | 说明 | 类比 |
| :--- | :--- | :--- |
| Tenant | 顶级隔离单元，代表团队或组织 | 实例/集群 |
| Database | 租户下逻辑空间，区分项目或应用 | 数据库实例 |
| Collection | **核心单元**，存储一组向量记录，查询最小单位 | 数据表 |
| Document | 原始文本块，embedding 通常基于文档内容生成 | 表行 |
| Embedding | 模型生成的数值数组，代表语义 | 行内字段 |
| Metadata | 可过滤的键值对，用于检索前后过滤 | 其他列 |

- **Collection** 是读写与查询的边界；同一 Collection 内文档共享 embedding 函数与索引策略。
- 与 Spring AI `VectorStore` 概念对应：Document + metadata + vector 三元组持久化后通过 similarity search 召回。

### 面试常问

**问**：ChromaDB 是什么？其核心数据单元是什么？与关键词检索有何区别？

**答**：专为 AI/RAG 设计的轻量向量库，核心是 **Collection**（类比表）。检索基于 embedding 语义相似度而非关键词匹配，适合「意思相近但措辞不同」的召回场景。

## ChromaDB Python 快速上手

> **模块**：索引与存储 | **标签**：ChromaDB, Python, 元数据过滤 | **更新**：2026-05-28

### 核心概念

ChromaDB 典型流程：创建持久化客户端 → 创建 Collection（指定 embedding 函数）→ `add` 文档与元数据 → `query` 语义检索；支持 `where` 元数据过滤。

### 要点

1. **安装**：`pip install chromadb`（默认 embedding 需 `sentence-transformers`）。
2. **客户端**：`PersistentClient(path=...)` 本地持久化；亦支持内存/服务端模式。
3. **写入**：`collection.add(documents, metadatas, ids)`，embedding 可由内置函数自动计算。
4. **检索**：`collection.query(query_texts, n_results)` 返回 documents、metadatas、distances。
5. **过滤**：`where={"country": "日本"}` 在语义检索前缩小候选集。

### 代码示例

```bash
pip install chromadb
```

```python
import chromadb
from chromadb.utils import embedding_functions

# 1. 创建客户端（使用本地持久化目录）
client = chromadb.PersistentClient(path="./chroma_data")

# 2. 创建集合（需指定 embedding 函数，此处使用默认的 all-MiniLM-L6-v2）
collection = client.create_collection(
    name="my_knowledge_base",
    embedding_function=embedding_functions.SentenceTransformerEmbeddingFunction()
)

# 3. 准备数据：文档、元数据、唯一 ID
documents = [
    "巴黎是法国的首都，以埃菲尔铁塔闻名。",
    "东京是日本的首都，以樱花和寿司闻名。",
    "北京是中国的首都，拥有故宫和长城。"
]
metadatas = [
    {"country": "法国", "feature": "铁塔"},
    {"country": "日本", "feature": "樱花"},
    {"country": "中国", "feature": "长城"}
]
ids = ["id1", "id2", "id3"]

# 4. 添加数据到集合
collection.add(
    documents=documents,
    metadatas=metadatas,
    ids=ids
)

# 5. 执行语义查询
query_text = "哪个国家的首都有著名的高塔？"
results = collection.query(
    query_texts=[query_text],
    n_results=2  # 返回最相似的 2 条结果
)

# 6. 查看结果
print("查询结果：")
for doc, meta, dist in zip(results['documents'][0], results['metadatas'][0], results['distances'][0]):
    print(f"文档: {doc}\n元数据: {meta}\n距离: {dist}\n")

# 7. 带元数据过滤的查询
filtered_results = collection.query(
    query_texts=["首都美食"],
    where={"country": "日本"},   # 仅查询 country 为日本的数据
    n_results=1
)
print("过滤后的查询结果：", filtered_results['documents'])
```

- 运行环境：Python 3.8+；需安装 `chromadb` 与 `sentence-transformers`（默认 embedding）。

### 面试常问

**问**：ChromaDB 如何实现「语义检索 + 元数据过滤」？

**答**：`query` 先将查询文本 embed，再在 Collection 内做 ANN 相似搜索；`where` 参数在检索链路中附加 metadata 条件（如 `country=日本`），实现租户/类别级过滤。

## 主流向量数据库选型对比

> **模块**：索引与存储 | **标签**：VectorStore, 选型, Milvus, Weaviate | **更新**：2026-05-28

### 核心概念

向量库选型需权衡**部署复杂度、规模、混合检索能力与运维成本**：原型与小规模优先 ChromaDB；亿级生产选 Milvus/Weaviate；免运维选 Pinecone；纯算法实验可用 FAISS。

### 要点

| 项目 | 特点 | 部署 | 擅长场景 | 学习曲线 |
| :--- | :--- | :--- | :--- | :--- |
| **ChromaDB** | 简单轻量、API 友好，`pip install` 即用 | 嵌入式/单机 | RAG 原型、小规模、学习实验 | 低 |
| **Weaviate** | 向量+关键词混合搜索，GraphQL 接口 | 单机/集群 | 需混合查询的生产（如电商搜索） | 中 |
| **Milvus** | 云原生、高并发高可用，社区活跃 | 分布式集群 | 大规模向量检索生产 | 高 |
| **Qdrant** | 性能强、过滤能力丰富 | 单机/集群 | 精细过滤与高性能检索 | 中 |
| **FAISS** | Meta 算法库（非完整 DB），高效 ANN | 嵌入式库（内存） | 学术研究、定制化算法、无需持久化 | 中 |
| **Pinecone** | 全托管云服务，免运维 | 云服务 | 不想自管基础设施的生产应用 | 低 |

**选型速查**

| 场景 | 推荐 |
| :--- | :--- |
| 个人/小团队快速 RAG 原型 | ChromaDB |
| 亿级向量、高并发、高可用 | Milvus / Weaviate |
| 免运维、专注业务 | Pinecone / Qdrant（托管或自管视团队能力） |
| 仅需相似度算法、不需 DB 能力 | FAISS |

- 与 Spring AI 集成：生产常见 PgVector、Elasticsearch；Chroma 多用于 Python 生态原型或非 Spring 栈。

### 面试常问

**问**：ChromaDB 和 Milvus 分别适合什么场景？FAISS 为什么不算完整向量数据库？

**答**：ChromaDB 适合原型与小规模 RAG，零配置上手；Milvus 面向亿级分布式生产。FAISS 是内存中的 ANN 算法库，不提供持久化、多租户、元数据过滤等数据库能力，适合实验而非在线服务。
