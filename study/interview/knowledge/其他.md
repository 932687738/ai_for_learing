## Cursor 多智能体开发最佳实践

> **模块**：其他 | **标签**：Cursor, IDE, 工程实践 | **更新**：2026-05-28

### 核心概念

在 Cursor 中模拟多智能体时，关键是**角色定义清晰、上下文严格传递、人类保留审核权**；重复性生成交给 AI，架构决策与关键业务逻辑由人把关。

### 要点

| 实践 | 说明 |
| :--- | :--- |
| 分角色 Rules | 每个智能体独立 `.cursor/rules/*.mdc`，通过 `@规则名` 切换 |
| 明确输出格式 | 在角色定义中强制 Markdown PRD、设计文档或指定语言代码块 |
| 增量迭代 | 分模块逐步生成，避免一次要求全量功能 |
| 人类审核 | 生成代码须 review 后再合并，不自动信任输出 |
| Apply 应用 diff | 利用 Cursor Apply 将 AI diff 直接落盘，提高效率 |
| `// @ai` 注释 | 在代码中写引导注释，让 AI 补全具体实现片段 |
| 公共约束 | `.cursor/prompts/common.md` 存放跨角色通用规范，每轮可 `@` 引用 |

- **流程管理者**：人负责触发各 `@角色`、检查阶段产出、Git merge 与冲突解决。
- **适用场景**：新项目从零搭建、遗留系统分模块迭代维护均可复用。
- **边界**：本实践描述 IDE 工作流，与 Spring AI `ChatClient`/Agent 运行时 API 无直接耦合。

### 面试常问

**问**：用 Cursor 做多智能体协同时，有哪些必须遵守的工程习惯？

**答**：分文件定义角色职责与输出格式；用 `@` 引用上一阶段文档再生成下一阶段；小步增量、人工 review 后合并；Composer/Apply 加速落盘，但不让 AI 替代架构决策。

## RAG、知识图谱与向量库概念对比

> **模块**：其他 | **标签**：RAG, 知识图谱, 向量检索 | **更新**：2026-05-28

### 核心概念

RAG、知识图谱、向量库与 GraphRAG 解决不同层面的「知识接入与推理」问题，选型前需明确任务是语义匹配、关系推理还是跨文档全局分析。

### 要点

| 概念 | 核心思想 | 典型用途 |
| :--- | :--- | :--- |
| **RAG** | 生成前从外部知识库检索上下文 | 降幻觉、接入私有数据 |
| **知识图谱** | 实体（节点）+ 关系（边）的图网络 | 多跳推理、可解释关系问答 |
| **向量库** | 文本→高维向量，ANN 语义相似检索 | 模糊语义匹配 |
| **GraphRAG** | 知识图谱 + RAG，可融合向量检索 | 跨文档复杂推理、全局性问题 |

### 面试常问

**问**：RAG、知识图谱和向量检索各自解决什么问题？GraphRAG 又是什么？

**答**：RAG 用检索增强生成；向量库做语义相似匹配；知识图谱显式建模实体关系以支持多跳推理；GraphRAG 将图结构与 RAG 结合，适合需要关系遍历与全局视角的复杂问答。

## GraphRAG 原理与会话式检索

> **模块**：其他 | **标签**：GraphRAG, Neo4j | **更新**：2026-05-28

### 核心概念

GraphRAG 在图结构上做检索增强：默认每次 Cypher/图查询**无状态独立**；会话式场景需应用层维护历史实体并注入后续查询，配合缓存加速重复访问。

### 要点

- **默认行为**：单次搜索不自动复用前次图遍历结果。
- **加速**：应用层查询缓存；图库热点节点/路径缓存。
- **会话式 GraphRAG**：上层维护对话状态，将历史识别出的实体（如餐厅名）传入下一轮 Cypher 扩展查询。

### 代码示例

```cypher
// 第一次：查找「山本屋」
MATCH (r:Restaurant {name: '山本屋'}) RETURN r

// 第二次：基于历史实体扩展（需应用层传入上下文）
MATCH (r:Restaurant {name: '山本屋'})-[:LOCATED_IN]->(city:City)
MATCH (other:Restaurant)-[:LOCATED_IN]->(city)
WHERE other.vegan_friendly = true
RETURN other
```

### 面试常问

**问**：GraphRAG 第二次搜索为什么会「慢」或感觉没用到第一次结果？如何优化？

**答**：图查询默认无状态，不会自动继承上轮实体上下文。应在应用层维护会话实体并改写 Cypher，同时加查询/热点节点缓存；复杂多轮可显式传递 `LOCATED_IN` 等关系扩展条件。

## 知识图谱多跳推理示例

> **模块**：其他 | **标签**：知识图谱, Cypher | **更新**：2026-05-28

### 核心概念

以餐厅领域为例：将非结构化文本抽为实体与关系后，可按**属性检索、一跳邻居、多跳推理**不同粒度回答复合问题（如「同区域还有哪些素食餐厅」）。

### 要点

**原始文档示例**

- 山本屋：日料，朝阳区，安静，不适合儿童，提供素食。
- 樱花园：日料，朝阳区，欢迎儿童，素食需提前告知。

**检索粒度**

| 粒度 | 用途 |
| :--- | :--- |
| 属性检索 | 直接查实体属性 |
| 一跳 | 查直接关系邻居 |
| 多跳 | 沿关系链推理（同区域+素食约束） |

### 代码示例

```cypher
CREATE (:Restaurant {name:'山本屋', type:'日料', district:'朝阳区', kid_friendly:false, vegan_friendly:true})
CREATE (:Restaurant {name:'樱花园', type:'日料', district:'朝阳区', kid_friendly:true, vegan_friendly:'warning'})

MATCH (a:Restaurant {name:'山本屋'}), (b:Restaurant {name:'樱花园'})
CREATE (a)-[:LOCATED_IN]->(:City {name:'朝阳区'})
CREATE (b)-[:LOCATED_IN]->(:City {name:'朝阳区'})
```

```cypher
MATCH (r:Restaurant {name:'山本屋'})-[:LOCATED_IN]->(city:City)
MATCH (other:Restaurant)-[:LOCATED_IN]->(city)
WHERE other.vegan_friendly = true OR other.vegan_friendly = 'warning'
RETURN other.name
```

### 面试常问

**问**：知识图谱相比纯向量 RAG，在多跳问答上有什么优势？举例说明。

**答**：图显式建模 `LOCATED_IN`、属性约束等关系，可写 Cypher 做「同区域且素食友好」的多跳过滤；纯向量检索难以可靠表达结构化关系链，易漏召或误召。
