## Cursor 多智能体开发最佳实践

> **模块**：其他 | **标签**：Cursor, IDE, 工程实践 | **更新**：2026-05-28

### 核心概念

在 Cursor 中模拟多智能体时，关键是**角色定义清晰、上下文严格传递、人类保留审核权**；重复性生成交给 AI，架构决策与关键业务逻辑由人把关。

### 要点

| 实践 | 说明 |
| :--- | :--- |
| 分角色 Rules | 每个智能体独立 `.cursor/rules/*.mdc`，通过 `@规则名` 切换 |
| 明确输出格式 | 在角色定义中强制 Markdown PRD、设计文档或指定语言代码块 |
| 增量迭代 | 分模块逐步生成，避免一次要求全量功能 |
| 人类审核 | 生成代码须 review 后再合并，不自动信任输出 |
| Apply 应用 diff | 利用 Cursor Apply 将 AI diff 直接落盘，提高效率 |
| `// @ai` 注释 | 在代码中写引导注释，让 AI 补全具体实现片段 |
| 公共约束 | `.cursor/prompts/common.md` 存放跨角色通用规范，每轮可 `@` 引用 |

- **流程管理者**：人负责触发各 `@角色`、检查阶段产出、Git merge 与冲突解决。
- **适用场景**：新项目从零搭建、遗留系统分模块迭代维护均可复用。
- **边界**：本实践描述 IDE 工作流，与 Spring AI `ChatClient`/Agent 运行时 API 无直接耦合。

### 面试常问

**问**：用 Cursor 做多智能体协同时，有哪些必须遵守的工程习惯？

**答**：分文件定义角色职责与输出格式；用 `@` 引用上一阶段文档再生成下一阶段；小步增量、人工 review 后合并；Composer/Apply 加速落盘，但不让 AI 替代架构决策。

## RAG、知识图谱与向量库概念对比

> **模块**：其他 | **标签**：RAG, 知识图谱, 向量检索 | **更新**：2026-05-28

### 核心概念

RAG、知识图谱、向量库与 GraphRAG 解决不同层面的「知识接入与推理」问题，选型前需明确任务是语义匹配、关系推理还是跨文档全局分析。

### 要点

| 概念 | 核心思想 | 典型用途 |
| :--- | :--- | :--- |
| **RAG** | 生成前从外部知识库检索上下文 | 降幻觉、接入私有数据 |
| **知识图谱** | 实体（节点）+ 关系（边）的图网络 | 多跳推理、可解释关系问答 |
| **向量库** | 文本→高维向量，ANN 语义相似检索 | 模糊语义匹配 |
| **GraphRAG** | 知识图谱 + RAG，可融合向量检索 | 跨文档复杂推理、全局性问题 |

### 面试常问

**问**：RAG、知识图谱和向量检索各自解决什么问题？GraphRAG 又是什么？

**答**：RAG 用检索增强生成；向量库做语义相似匹配；知识图谱显式建模实体关系以支持多跳推理；GraphRAG 将图结构与 RAG 结合，适合需要关系遍历与全局视角的复杂问答。

## GraphRAG 原理与会话式检索

> **模块**：其他 | **标签**：GraphRAG, Neo4j | **更新**：2026-05-28

### 核心概念

GraphRAG 在图结构上做检索增强：默认每次 Cypher/图查询**无状态独立**；会话式场景需应用层维护历史实体并注入后续查询，配合缓存加速重复访问。

### 要点

- **默认行为**：单次搜索不自动复用前次图遍历结果。
- **加速**：应用层查询缓存；图库热点节点/路径缓存。
- **会话式 GraphRAG**：上层维护对话状态，将历史识别出的实体（如餐厅名）传入下一轮 Cypher 扩展查询。

### 代码示例

```cypher
// 第一次：查找「山本屋」
MATCH (r:Restaurant {name: '山本屋'}) RETURN r

// 第二次：基于历史实体扩展（需应用层传入上下文）
MATCH (r:Restaurant {name: '山本屋'})-[:LOCATED_IN]->(city:City)
MATCH (other:Restaurant)-[:LOCATED_IN]->(city)
WHERE other.vegan_friendly = true
RETURN other
```

### 面试常问

**问**：GraphRAG 第二次搜索为什么会「慢」或感觉没用到第一次结果？如何优化？

**答**：图查询默认无状态，不会自动继承上轮实体上下文。应在应用层维护会话实体并改写 Cypher，同时加查询/热点节点缓存；复杂多轮可显式传递 `LOCATED_IN` 等关系扩展条件。

## 知识图谱多跳推理示例

> **模块**：其他 | **标签**：知识图谱, Cypher | **更新**：2026-05-28

### 核心概念

以餐厅领域为例：将非结构化文本抽为实体与关系后，可按**属性检索、一跳邻居、多跳推理**不同粒度回答复合问题（如「同区域还有哪些素食餐厅」）。

### 要点

**原始文档示例**

- 山本屋：日料，朝阳区，安静，不适合儿童，提供素食。
- 樱花园：日料，朝阳区，欢迎儿童，素食需提前告知。

**检索粒度**

| 粒度 | 用途 |
| :--- | :--- |
| 属性检索 | 直接查实体属性 |
| 一跳 | 查直接关系邻居 |
| 多跳 | 沿关系链推理（同区域+素食约束） |

### 代码示例

```cypher
CREATE (:Restaurant {name:'山本屋', type:'日料', district:'朝阳区', kid_friendly:false, vegan_friendly:true})
CREATE (:Restaurant {name:'樱花园', type:'日料', district:'朝阳区', kid_friendly:true, vegan_friendly:'warning'})

MATCH (a:Restaurant {name:'山本屋'}), (b:Restaurant {name:'樱花园'})
CREATE (a)-[:LOCATED_IN]->(:City {name:'朝阳区'})
CREATE (b)-[:LOCATED_IN]->(:City {name:'朝阳区'})
```

```cypher
MATCH (r:Restaurant {name:'山本屋'})-[:LOCATED_IN]->(city:City)
MATCH (other:Restaurant)-[:LOCATED_IN]->(city)
WHERE other.vegan_friendly = true OR other.vegan_friendly = 'warning'
RETURN other.name
```

### 面试常问

**问**：知识图谱相比纯向量 RAG，在多跳问答上有什么优势？举例说明。

**答**：图显式建模 `LOCATED_IN`、属性约束等关系，可写 Cypher 做「同区域且素食友好」的多跳过滤；纯向量检索难以可靠表达结构化关系链，易漏召或误召。

## AI Agent 沙盒隔离与安全

> **模块**：其他 | **标签**：沙盒, 容器, 指令注入 | **更新**：2026-06-06

### 核心概念

沙盒通过隔离环境与最小权限，在假定代码不可信的前提下防御命令注入、数据外泄与权限越权；AI Agent 执行不受信代码时尤为关键。

### 要点

**五类策略**：
1. 进程/命名空间隔离（Docker/Kata）——独立文件系统与网络栈
2. 语言级沙盒（RestrictedPython 等）——白名单 API、禁用 child_process/fs
3. 网络沙盒——默认禁出站或代理白名单
4. 输入/输出验证——参数化查询、输出转义
5. 运行时监测——syscall 审计与异常检测

**构建四步**：风险评估 → 选型（容器/语言/Hypervisor/硬件）→ 实施 Namespace/cgroups/Seccomp/网络控制 → 纵深防御与一次性生命周期。

**Docker 实践**：非 root 用户、`--cap-drop=ALL`、`--read-only`、`--network none`、资源限额、seccomp 白名单。

**局限**：存在逃逸风险；对间接提示词注入仅辅助，需配合 HITL 与三层隔离模型。

### 代码示例

```bash
docker run --rm --cap-drop=ALL --read-only --network none \
  --memory=512m --cpus=0.5 your_sandbox_image
```

### 面试常问

**问**：沙盒如何预防 Agent 安全与指令注入？

**答**：隔离执行环境、最小权限、禁网或白名单出站、syscall 过滤与行为审计；假定代码不可信，高危操作加 HITL；多层机制组合，用完即毁容器。

## Fine-tuning 微调模型选型

> **模块**：其他 | **标签**：Fine-tuning, LoRA, QLoRA | **更新**：2026-06-06

### 核心概念

微调在预训练模型上用领域数据更新全部或部分参数，将通用模型「内化」为领域专家；与 Few-shot 的上下文学习相对，适合数据充足、高精度生产场景。

### 要点

| 维度 | Fine-tuning | Few-shot |
| :--- | :--- | :--- |
| 参数更新 | 是 | 否 |
| 数据量 | 通常 1000+ | 2–10 示例 |
| 成本 | GPU+标注高 | 极低 |
| 效果上限 | 高（垂直 SOTA） | 良好但有限 |

**主流方法**：全量微调（效果最好、成本最高）→ LoRA/QLoRA（0.1–1% 可训练参数，消费级 GPU）→ P-Tuning（软提示向量，适合任务开关）。

**流程**：数据准备（约 60% 工作量）→ 选型与超参 → 监控损失/早停 → 验证测试集；业务变化需增量微调。

### 面试常问

**问**：何时用 Fine-tuning 而非 Few-shot？

**答**：有充足标注数据、需生产级稳定高精度、Few-shot 提升触顶时用 LoRA/QLoRA 微调；快速验证或数据极少时优先 Few-shot 或 RAG。

## 知识图谱存储模型与起始节点定位

> **模块**：其他 | **标签**：知识图谱, Neo4j, Cypher, RDF | **更新**：2026-06-06

### 核心概念

知识图谱主要有属性图（Neo4j，节点-有向关系-属性，免索引邻接遍历）与 RDF 三元组（主-谓-宾，SPARQL 声明式查询）两种存储；查询先定位起始节点再沿关系推理。

### 要点

**属性图**：`MATCH (p:Person {name:"郭帆"})-[:DIRECTED]->(m:Movie) RETURN m.title`；可变长路径 `[:FRIEND*1..3]`；APOC 扩展遍历。

**RDF**：`?person :name "郭帆" . ?person :directed ?movie .`

**起始节点定位**：用业务属性（name/ID）+ 索引；避免依赖 Neo4j 内部 id()；模糊用 CONTAINS/FILTER。

**推理**：前向/后向链规则（如传递性管理关系）推导未显式存储的知识。

### 代码示例

```cypher
CREATE INDEX FOR (p:Person) ON (p.name)
MATCH (p:Person {name: "郭帆"})-[:DIRECTED]->(m:Movie)
RETURN m.title
```

### 面试常问

**问**：知识图谱如何存储？如何找到第一个节点并往后推理？

**答**：属性图用节点关系指针高效遍历，RDF 用三元组+索引；先用 MATCH/WHERE 按业务键定位起始节点，再沿关系模式匹配多跳；复杂路径可用 APOC 或规则推理。

## 冷启动与长尾问题

> **模块**：其他 | **标签**：冷启动, 长尾, Text2SQL | **更新**：2026-06-06

### 核心概念

冷启动是缺乏历史数据/样本导致难以响应新用户、新库或新题型；长尾是低频但种类极多的查询累积占比大、头部训练难以覆盖。

### 要点

| 维度 | 冷启动 | 长尾 |
| :--- | :--- | :--- |
| 本质 | 从零开始无样本 | 有但极少 |
| 时机 | 上线初期/新数据源 | 运行期持续出现 |
| 解法 | DDL Schema Linking、主动询问、规则兜底、合成数据 | 查询分解、动态 Few-shot、Observation 自修复、主动学习入库 |

**Text2SQL 实践**：冷启动读 DDL+通用 Few-shot；成功 (问题,SQL) 入向量库；长尾用 DIN-SQL/子查询分解 + ReAct 多轮修正，失败案例分类后回流 Few-shot 库或微调。

### 面试常问

**问**：什么是冷启动和长尾问题？如何解决？

**答**：冷启动是没有历史样本，靠元数据、合成数据和 HITL 引导；长尾是罕见查询多，靠分解、动态检索相似案例和执行反馈自修复，并将成功案例持续写入记忆库渐进改善。
